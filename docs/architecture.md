# ADR-001: портал и редакция

Ссылки подразделений редактируются в админке. Миграция 4 добавляет таблицу
`division_links(name PRIMARY KEY, url NOT NULL)` без изменения событий и медиа.
Справочник городов находится в `contracts/divisions.json`; исходные адреса
каналов не активируют карточки. По умолчанию все карточки без перехода.
`PUT /api/admin/divisions` проверяет сессию, CSRF, известное название и
абсолютный HTTP(S)-адрес либо пустую строку. UPSERT повторяем; публичный
`/api/content` возвращает настройки. Очистка ссылки отключает переход.
Старые payload content без divisions читаются как неактивный каталог.
Миграция проверена на пустой и заполненной SQLite и повторном открытии.
Удаление таблицы уничтожит настройки, автоматического downgrade нет.

Миграция 5 расширяет division_links полями coordinator, contact, vk, max,
telegram, email, website (TEXT NOT NULL DEFAULT ''). Они необязательны в API:
отсутствующее поле сохраняет прежнее значение при обновлении, пустая строка
очищает его. Проверяются длины, формат почты и HTTP(S)-ссылки. Поля возвращаются
редакции через /api/admin/content; публичный ответ по-прежнему содержит только
название и адрес перехода. Миграция сохраняет существующие ссылки v4, проверены
повторное открытие, integrity_check и foreign_key_check.

Статус: принято для начальной реализации по поручению пользователя, 08.11.2026.

React + TypeScript + Tailwind CSS / Vite обслуживают публичные страницы и
редакцию. Frontend разделён на app, pages и shared по FSD; отдельные features
пока не нужны. Направления импортов и циклы проверяет `npm run lint`.
TanStack Query владеет серверными данными. Локальные формы владеют черновиками.

Один Express-процесс владеет API. Канонические схемы контрактов —
`contracts/content.ts` (Zod), общие для клиента и сервера. Transport проверяет
вход, авторизацию и формат ответа; repository выполняет параметризованный SQL;
media-file определяет разрешённые сигнатуры файлов. БД и файлы обслуживаются
одним экземпляром приложения с постоянными Docker volumes.

Альтернативы: внешняя headless CMS уменьшит собственный код админки, но потребует
отдельного продукта и модели развёртывания. PostgreSQL нужен при нескольких
писателях/репликах; сейчас выбран SQLite для одного VPS без дополнительных служб.
Объём нагрузки не известен; способность к конкретному трафику не измерялась.

## Данные и инварианты

| Таблица | Сценарий и владелец | Ключ/связи | Ограничения и удаление |
| --- | --- | --- | --- |
| events | Редакция создаёт и публикует анонс | UUID, связей нет | Поля NOT NULL; published 0/1; удаление явное из админки |
| media | Редакция загружает файл и описание | UUID, URL UNIQUE | kind image/video; published 0/1; удаление метаданных и попытка очистки файла |
| sessions | Вход администратора | sid, связей нет | TTL 8 часов; истёкшие записи очищаются при записи сессии |
| migrations | Версии схемы | version PRIMARY KEY | Миграция 1 применяется транзакционно и повторяемо |

Ожидаемая кардинальность неизвестна. Начальная версия возвращает до 500 записей
каждого типа, без пользовательской пагинации; перед расширением архива необходима
пагинация и фильтрация календаря на сервере. Каталог подразделений — версионируемый
справочник, изменения проходят PR.

Даты хранятся в UTC ISO-8601; редактор принимает время Москвы. Индекс
`events(published, startsAt, id)` обслуживает публичный отбор и стабильную
сортировку. Media сортируется по порядку добавления. Измерений на большой БД нет.
Каждая SQL-запись атомарна; уникальность URL проверяется БД. При отказе INSERT
после записи файла файл удаляется. Между БД и файловой системой общей транзакции
нет: аварийное завершение в промежутке может оставить лишний файл. При удалении
сначала удаляются метаданные, поэтому сбой очистки не открывает удалённый материал.

## Доступ

Один администратор с bcrypt-хешем пароля из окружения; общего пароля по умолчанию
нет. Сессии SQLite, HttpOnly/SameSite=Strict, Secure в production, ротация sid при
входе, CSRF-токен на изменениях, лимит попыток входа по IP. Поле published не
является авторизацией: сервер отдельно проверяет сессию и доступ к файлу.
Публичный GET не возвращает черновики, файлы черновиков требуют админской сессии.
Файлы ограничены 30 МБ, именуются UUID, допускаются PNG/JPEG/WebP/MP4 по сигнатуре.
Полная антивирусная проверка и перекодирование видео в этот этап не входят.

HTTPS заканчивается на Caddy; порт приложения не публикуется наружу в Compose.
Caddy — единственный доверенный proxy hop. Секреты не входят в образ/репозиторий.

## Проверка и эксплуатация

Пустая/повторная миграция и сохранение заполненной SQLite проверяются тестами,
как и integrity_check/foreign_key_check. Предыдущей версии схемы ещё нет;
downgrade не заявлен. Новые миграции добавляются с новым номером.

Обновление — опубликованный образ по неизменяемому тегу из main. Резервировать
следует SQLite через Online Backup API и uploads вместе с привязкой к версии.
Возврат к старому образу допустим только при совместимости схемы; реальное
восстановление из production backup ещё не проверялось.

Критерии пересмотра: необходимость нескольких экземпляров, архив >500 записей,
крупные видео >30 МБ, несколько редакторов с разными правами, требования к RPO/RTO.

## ADR-002: хронология медиатеки

Миграция 2 добавляет `media.eventDate TEXT NOT NULL DEFAULT ''`.
ISO-дата `YYYY-MM-DD` валидируется на HTTP-границе; пустая строка означает
неизвестную дату. Поле необязательное для старых API-клиентов. PUT без поля
сохраняет существующую дату, явная пустая строка очищает её. Multipart допускает
четыре поля: заголовок, описание, дата, статус публикации. Исторический диапазон
и дата публикации, если она используется вместо даты события, поясняются в тексте.

Клиент сортирует копию массива по дате, неизвестные даты — в конце. Сохраняется
лимит 500 материалов: перед ростом архива нужна серверная пагинация и сортировка.
Поле позволяет фильтровать годы без разбора произвольных описаний редактора.

Перед локальным применением сохранена копия `data/portal-before-chronology.sqlite`.
Миграция проверена на заполненной v1 БД, повторном открытии и integrity_check.
Возврат к старому серверу с позиционным INSERT в media после миграции 2 не
поддерживается: для отката требуется остановка приложения и восстановление
совместимой копии БД. Для старых HTTP-клиентов совместимость проверена отдельно.

## ADR-003: страницы материалов и фотогалереи

Публичная карточка ведёт на `/media/:id`; полное описание остаётся в существующем
`description`. Клиент использует общий query `content`; неизвестный или снятый
с публикации материал показывает состояние «Материал не найден».

Миграция 3 добавляет `media_images(id,mediaId,url)`: FK на media с ON DELETE CASCADE,
уникальный URL и индекс владельца. Обложки и прежние записи не изменяются.
API отдаёт дополнительный необязательный массив `images: [{id,url}]`.
POST `/api/admin/media/:id/images` принимает один PNG/JPEG/WebP до 30 МБ;
DELETE `/api/admin/media/:id/images/:imageId` удаляет фотографию только у указанного
материала. Обе операции требуют административную сессию и CSRF. Тип проверяется
по сигнатуре файла. Файлы галереи проходят ту же проверку видимости, что обложка.
При удалении материала удаляются его строки и файлы. При ошибке вставки новый
файл удаляется; отсутствующий файл при удалении не блокирует удаление записи.

Карусель использует паттерн arhdesign: крупный кадр, миниатюры, счётчик,
замкнутые стрелки, клавиатура и свайп. Полноэкранный просмотр использует нативный
modal dialog (Escape, удержание и возврат фокуса). Снимки целиком вписываются
в область просмотра; автоматической смены нет. Система тем сохраняется.

Перед наполнением сохранена локальная копия `data/portal-before-galleries.sqlite`.
Повторный импорт не меняет тексты редактора и сверяет фотографии по SHA-256.
Откат интерфейса на прежний код совместим с дополнительной таблицей;
удаление таблицы уничтожило бы связи фото, поэтому down-миграции нет.

## ADR-004: публикации и площадки редакции

Владелец данных — Store; изменения доступны только администратору с CSRF.
PATCH `/api/admin/:kind/:id/publication` принимает `{published:boolean}` для
`events`, `media`, `divisions`, `channels`; повтор устанавливает тот же статус.
Идентификатор подразделения — название из каталога; остальных сущностей — UUID.
Смена статуса атомарна одним UPDATE, не меняет текст и не удаляет файлы.
Публичный API исключает черновики всех четырёх типов. Контакты координаторов
по-прежнему доступны только редактору. Каталог городов остаётся виден целиком;
ссылка работает только для опубликованной записи с непустым URL.

Миграция 6 транзакционно добавляет division_links.published (старые записи
опубликованы для сохранения поведения) и channels. Площадки имеют PK id,
обязательные name/note/short/url и published с CHECK 0/1. Связей нет; удаление
явное, без каскадов. Начальные четыре площадки переносятся один раз из
contracts/channels.json. Повторное открытие БД не восстанавливает удалённые ссылки.
POST/PUT/DELETE `/api/admin/channels` обслуживают редактор; URL ограничен HTTP(S).
Публичные футер и медиапространство читают один список из API, без статического
fallback, который мог бы вернуть снятые с публикации ссылки.

Объём площадок — небольшой редакционный список; чтение по rowid и фильтру
published полным проходом, отдельный индекс не нужен. Новая миграция расширяет
схему без удаления данных; старый сервер не должен использоваться после начала
работы с черновиками подразделений, поскольку не знает их статуса.
Откат — исправление вперёд либо восстановление согласованной копии БД при
остановленном приложении. Down-миграции нет. Админка использует отдельную
композицию без публичных header/footer, с одним выходом и ссылкой просмотра сайта.


## ADR-005: явное назначение обновления сайта

Решение принято по уточнению владельца 08.11.2026: отдельная вкладка админки и
время, выбранное пользователем, вместо фиксированного ночного окна. Для небольшой
стартовой VPS сохраняется один app-контейнер; blue/green потребовал бы двух
процессов, совместимости миграций и большего запаса памяти. Безостановочность
при замене образа не заявляется; публикации контента не меняют процесс.

Store владеет deployments: UUID PK, version/scheduledAt/createdAt/status/detail
NOT NULL, без FK, без удаления истории через API. Ожидается небольшое число
релизов; последние 50 отображаются по createdAt,rowid. Миграция 7 добавляет
таблицу, CHECK статусов и частичный UNIQUE по константе для scheduled/running.
Транзакция IMMEDIATE сериализует создание и claim; условные UPDATE защищают
cancel/finish. Идентификаторы и версии не интерполируются в SQL. Времена UTC ISO;
в UI ввод/отображение МСК. Переходы: scheduled → running → succeeded|failed,
scheduled → cancelled; пропущенный запуск → failed. Отменённый/завершённый
релиз не запускается повторно. Сбой исполнителя → failed под хостовой блокировкой.

GET/POST/DELETE /api/admin/deployments защищены существующими session/CSRF;
в публичный content расписание не входит. POST принимает
scheduledAt минимум на минуту позже текущего времени; возвращает 409 при занятой
очереди. Все поля валидируются до записи. Хостовый systemd timer/runner имеет
Docker-доступ, веб-приложение его не получает. Единственная команда — смена
образа фиксированного repository с semver-тегом, после скачивания и проверки
времени. Runtime CLI включён в Dockerfile. Расписание сохраняется при рестарте.

Новая таблица не удаляет прежние данные. Предыдущий сервер не знает очередь:
при откате остановите таймер и проверьте отсутствие активного задания. Перед
реальной эксплуатацией нужны установка таймера на VPS, проверка времени/health,
доступности GHCR и восстановления; локальные проверки не заменяют этот этап.


Уточнение ADR-005: поле ручного ввода версии удалено по требованию владельца.
HTTP-ввод содержит только scheduledAt; существующий version старого клиента
игнорируется. Job schema по-прежнему содержит зафиксированную semver version.
До SQL-транзакции сервер определяет последний опубликованный стабильный образ
GHCR; при сетевой ошибке/пустом списке или отсутствии более новой версии очередь
не изменяется. Сетевые вызовы не удерживают SQLite write lock. Существующие
назначенные задания сохраняют прежний выбранный тег. Миграция не требуется.
