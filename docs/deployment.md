# VPS / Docker

Текущее состояние: работа локально, по уточнению пользователя от 08.11.2026.
VPS, домен и SSH не подключены; публичного production-деплоя нет. GitHub хранит
код и правила будущей доставки. Создавать релизный тег для просмотра дизайна не нужно.

## Релиз после приёмки

1. PR рабочей ветки в develop: format, ESLint/FSD, TypeScript, unit/integration,
   coverage 90% строк/ветвей, Cypress и проверочная компиляция.
2. PR develop → main с теми же проверками. Другие источники в main CI отклоняет.
3. Владелец создаёт новый неизменяемый тег MAJOR.MINOR.PATCH на принятом main.
   Workflow проверяет формат, принадлежность коммита удалённой main и повторно
   запускает проверки на самом теге. После сборки выполняется health/static smoke
   контейнера; только затем Docker-образ публикуется.
4. Workflow Deploy released version to VPS запускается вручную с принятым тегом
   из main. Environment production требует подтверждение SosnovichIvan.
   Укажите также назначенное UTC-время. Запуск разрешён не раньше него и не позже
   чем через 10 минут; скрипт передаёт версию/время и не меняет серверный .env.

GitHub rulesets запрещают изменение/удаление существующих Git-тегов, прямой push,
force push и удаление main/develop. Единственный bypass — User SosnovichIvan для
ревью в режиме pull_request. Он не обходит PR/quality-gate.

Workflow Actions закреплены SHA. PR выполняются на GitHub-hosted runner без
production secrets и не публикуют образ. Cypress использует временную тестовую БД.

## Когда будет выбран VPS

Нужен Linux с Docker Engine и Compose v2, доступный TCP 80/443 и UDP 443,
домен с DNS на сервер. Текущий release runner собирает linux/amd64; для ARM VPS
перед первым выпуском следует добавить соответствующую платформу Buildx.

На сервер копируются compose.yaml, Caddyfile, scripts/deploy.sh,
scripts/check-deploy-time.sh и scripts/run-scheduled-deploy.sh в одну директорию.
Скрипты должны иметь право исполнения. Нужны GNU date и util-linux flock (Linux).
Серверный .env должен содержать:

```dotenv
SITE_ADDRESS=your-domain.example
RELEASE_TAG=0.1.0
SESSION_SECRET=<random secret of at least 32 characters>
ADMIN_PASSWORD_HASH='<bcrypt hash, single quotes preserve dollar signs>'
```

Хеш можно получить локально без отправки пароля во внешние сервисы:

```sh
read -rs ADMIN_PASSWORD
export ADMIN_PASSWORD
node --input-type=module -e 'import { hash } from "bcryptjs"; console.log(await hash(process.env.ADMIN_PASSWORD,12))'
unset ADMIN_PASSWORD
```

Хеш и secret переносятся в серверный .env, права файла 0600. Пароль не попадает
в браузерный bundle или Docker build context. Локальные .env/пароль на VPS
не копируются. Single quotes защищают символы `$` хеша от Compose interpolation
([документация Docker](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation)).

Первое развёртывание из серверной директории:

```sh
./scripts/deploy.sh 0.1.0 2026-12-01T00:00:00Z
```

Caddy выдаёт HTTPS для домена. App не публикует порт на хост и работает от
непривилегированного пользователя с read-only root filesystem; БД/медиа в volumes.
Для приватного GHCR package серверу дополнительно нужен read-only package login;
публичный GitHub repository сам по себе не гарантирует публичность package.

## Подключение GitHub-деплоя

Repository Variables: DEPLOY_HOST, DEPLOY_USER, DEPLOY_PATH.
Environment production Secrets: DEPLOY_SSH_KEY, DEPLOY_KNOWN_HOSTS.

Использовать отдельного SSH-пользователя и ключ с ограниченной серверной командой,
соответствующей deploy.sh. Fingerprint сервера сверяется по доверенному каналу;
StrictHostKeyChecking не отключается. Изменения инфраструктуры VPS и создание
учётных записей в текущем локальном этапе не выполнялись.

## Данные и восстановление

Volumes portal-data и portal-uploads переживают замену контейнера. Не выполнять
`docker compose down -v` на сервере с данными. До релиза резервировать БД через
SQLite Online Backup API и каталог uploads в согласованную точку; хранить копии
вне VPS. Восстановление проверять в отдельной среде до заявления о его готовности.

Возврат приложения — deploy предыдущего тега, только если схема совместима.
Текущая схема v1 создаётся идемпотентно; production backup/restore и SSH-деплой
пока не проверялись. Опубликованный образ и Git-тег не заменяют резервную копию.


## Обновления по времени, выбранному в админке

Фиксированного ночного окна нет. Администратор открывает вкладку «Обновление
сайта», указывает дату/время по Москве, затем явно
нажимает «Запланировать обновление». Запись сохраняется в SQLite, допускается
одна ожидающая/выполняющаяся операция. До запуска её можно отменить; история
сохраняет результаты. Удаление материалов/публикации к этой очереди не относятся.

В локальном режиме DEPLOYMENT_SCHEDULER_ENABLED не задан: задания сохраняются
для проверки интерфейса, но исполнитель не запущен. Локальный сайт не обновляется
и VPS не создаётся. Для настоящего выполнения на VPS после первого выпуска:

1. Установите ops/severniy-update.service и .timer в /etc/systemd/system;
   исправьте WorkingDirectory/ExecStart на фактический каталог сайта. Сервис
   запускается на хосте с доступом к Docker; не давайте этот доступ веб-контейнеру.
2. Запустите systemctl daemon-reload и systemctl enable --now severniy-update.timer.
3. Добавьте DEPLOYMENT_SCHEDULER_ENABLED=true в серверный .env и примените при
   согласованном обновлении. Проверяйте systemctl status/list-timers и journalctl
   -u severniy-update.service. Этот флаг обозначает настройку, не мониторинг health
   самого таймера. Проверьте пробное задание до эксплуатации расписания.

Таймер опрашивает очередь раз в минуту. Перед скачиванием и заменой проверяется
назначенное UTC-время: старт не раньше него, с допуском опроса/подготовки до
10 минут после. Просроченное задание завершается ошибкой, не выполняется внезапно
после долгого простоя. Крупный образ лучше заранее скачать оператору; скачивание
через pull само не останавливает рабочий контейнер. Если pull затянулся за допуск,
замена блокируется. Два отдельных flock предотвращают параллельный разбор очереди
и параллельную замену приложения (включая ручной GitHub-деплой).

CLI внутри текущего app-контейнера атомарно забирает задание и сразу завершается.
Хост затем вызывает deploy.sh и записывает успех только после --wait/healthcheck.
Docker socket/SSH/пароль GitHub не доступны публичному приложению. После сбоя
хостового исполнителя следующая попытка под блокировкой отмечает зависший running
как failed; автоматического повтора/смены времени нет. При недоступном app запись
результата тоже может не пройти: сначала восстановите приложение, затем проверьте
журнал и очередь. Не подменяйте ошибку успешным статусом.

Один app-контейнер означает возможный перерыв на остановку/запуск/миграции, даже
с --wait: это проверка готовности, а не rolling deployment. Caddy при отказе
соединения отдаёт 503 с Retry-After: 60 и сообщением об обновлении (для /api — JSON).
Длительность перерыва на настоящем VPS пока не измерена. При неудаче запуска
нужны диагностика и совместимый предыдущий образ/резервная копия; автоматический
откат не выполняется из-за возможных несовместимых миграций. Окно не гарантирует
автоматическое восстановление после дефектного релиза.

Публикации/снятие материалов выполняют SQL-запись без рестарта Node/Docker;
проверка параллельных запросов API и публикаций даёт HTTP 200. Настройка расписания
также не останавливает сайт — замену начинает только хостовый исполнитель.


Версия в форме не вводится. При назначении сервер получает список опубликованных
стабильных semver-тегов фиксированного GHCR repository и выбирает самый новый
по числам major/minor/patch. Выбранный тег сохраняется в задании, не меняется
позже сам собой. Совпадающая/более старая версия, пустой реестр или ошибка сети
не создают задание. Для каждого запроса к реестру timeout 5 секунд; неполный
список с pagination отвергается. Приватный пакет без публичного read-доступа
вернёт ошибку: перед VPS-развёртыванием задайте доступность package для чтения.
Токен анонимного чтения не пишется в логи/БД/браузер. UPDATE_RELEASE_VERSION
может закрепить известный опубликованный тег в окружении сервера без ручного
поля админки; это также используется изолированным E2E, чтобы не обращаться
к настоящему реестру. По умолчанию такой фиксации нет. В локальном проекте до
первого опубликованного образа сервер честно сообщает отсутствие готовой версии.
